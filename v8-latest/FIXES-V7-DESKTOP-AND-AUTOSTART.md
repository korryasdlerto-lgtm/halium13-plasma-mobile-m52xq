# Как мы добились рабочего стола при первом запуске и настроили автозагрузку (в5→в6→в7)

## Проблема на старте
Первая загрузка свежепрошитого в5: 5+ минут без картинки, без SSH, без рабочего стола. Автозапуск контейнера был включён (как унаследовано из более ранних версий), и это создавало гонку между стартом контейнера, GPU-мостом и композитором, из-за которой ничего не поднималось предсказуемо.

## Шаг 1: диагностика через pstore, а не гадание
Когда устройство неожиданно перезагружалось, реальную причину давал `/sys/fs/pstore/console-ramoops-0` (ring buffer ядра, переживает reboot), а не догадки. Именно так один раз нашли чистый `reboot: Power down` (не краш — штатное выключение, вероятно от `HandlePowerKey`), а не аппаратный watchdog.

## Шаг 2: разорвали жёсткую зависимость от android-service@hwcomposer
Раньше `plasma-mobile-wf.service` жёстко зависел (`Requires=`/`After=`) от отдельного `android-service@hwcomposer.service`, который сам гонялся за внутренней готовностью контейнера и часто исчерпывал лимит перезапусков systemd ДО того, как контейнер вообще был готов. Убрали эту зависимость полностью — оставили только `40-droid-wait.conf` отключённым (переименован в `.disabled`, ничем не заменён).

Ключевая находка: у `plasma-mobile-wf.service` уже был собственный `ExecStartPre=/userdata/halium-gpu-bridge-setup.sh` + `Environment=ANDROID_ROOT=/android` — ровно тот же паттерн, что использует Дроидиан у `phosh.service` (там ВООБЩЕ нет промежуточного юнита). Значит отдельный `android-service@hwcomposer.service` был архитектурно лишним для этой конкретной задачи.

## Шаг 3: починили линковщик для HAL-сервисов (WiFi/RIL/медиа-кодек)
Обнаружили и исправили: bionic-линковщик не мог разрешить `libandroidicu.so` через APEX-namespace редирект — но ТОЛЬКО для non-root UID сервисов (wifi, radio). Обходной путь: копируем `libandroidicu.so libicu.so libicui18n.so libicuuc.so` из `/apex/com.android.i18n/lib64/` прямо в `/system/lib64/` внутри `mount.sh` (хук контейнера), сразу после вызова `linkerconfig`. Починило `vendor.wifi_hal_legacy`, `ril-daemon`, `vendor.ipacm`, медиа-кодек одним фиксом.

## Шаг 4: убрали экран блокировки навсегда
`kscreenlocker_greet` запускался с `--immediateLock` при каждом старте сессии по неясной причине (не через наш обычный QML-путь). Вместо погони за триггером — `chmod 000` на сам бинарник в `update-binary`. Гарантированно убивает процесс и не даёт ему запуститься снова, независимо от того, что его вызывает.

## Шаг 5: настоящая надёжная блокировка автозапуска контейнера
Первая попытка (закомментировать создание symlink'а автозапуска в `update-binary`) оказалась НЕНАДЁЖНОЙ — контейнер всё равно стартовал сам минимум дважды на разных загрузках. Взяли готовый, проверенный паттерн из Дроидиан v25:

```ini
# lxc@android.service.d/00-first-boot-gate.conf
[Unit]
ConditionPathExists=/userdata/CONTAINER_ENABLED
```

Это жёсткая проверка systemd, которая срабатывает НЕЗАВИСИМО от того, как юнит пытаются запустить (symlink автозапуска, зависимость другого юнита, ручной `systemctl start`). Включается только вручную:

```sh
# /usr/libexec/halium-enable-container.sh
touch /userdata/CONTAINER_ENABLED
systemctl start lxc@android.service
```

Маркер-файл живёт на `/data` и переживает обычные перезагрузки (только полная перепрошивка/wipe его сотрёт) — то есть один раз включил, и дальше контейнер стартует сам при каждой следующей загрузке, пока не переустановишь систему.

## Итоговый рабочий процесс после этой связки фиксов
1. Прошить zip (в6/в7)
2. Первая загрузка: контейнер НЕ стартует сам (чисто, без гонки)
3. Один раз вручную: `sh /usr/libexec/halium-enable-container.sh`
4. Дальше при каждой следующей загрузке контейнер поднимается сам, и следом `plasma-mobile-wf.service` (уже не завязанный на отдельный `android-service@hwcomposer.service`) сам дожидается готовности GPU-моста через собственный `ExecStartPre` и поднимает рабочий стол с реальным GPU-рендерингом (`wayfire` держит открытым `/dev/kgsl-3d0`).

## Известные грабли по пути (см. память проекта для полного списка)
- Монтирование `rootfs.img` через `loop,rw` прямо в TWRP дважды роняло устройство (`__fput() for loop0 file is not finished for 180 sec` → hardware watchdog). Безопасный способ: `adb push` файлы в `/tmp` заранее, потом один плотный блок `mount && cp && sync && umount`.
- После рестарта `plasma-mobile-wf.service` (не полной перезагрузки) остаются "осиротевшие" `kwin_wayland`/`kwin_wayland_wrapper`, которые не убиваются вместе с юнитом — их надо явно `kill -9` перед повторным стартом, иначе всё работает непредсказуемо.
- `zip` для флеш-архива нужно собирать ИЗ ВНУТРИ папки версии (`cd в7 && zip -9 -r ../out.zip .`), не снаружи с именем папки как аргументом — иначе в архиве появляется лишний префикс пути и TWRP не находит `update-binary`.
