# в5: расследование экрана блокировки (LockScreenSplash / "Locking...")

Дата: 2026-07-31 (продолжение марафонской ночной сессии).

## Симптом

После первого запуска `plasma-mobile-wf.service` (и почти при каждом
последующем перезапуске/сбросе профиля) на экране появляется чёрный
полноэкранный оверлей с логотипом Debian и текстом "Locking..." (иногда
"Locked"), который либо висит вечно, либо проявляется периодически.

## Находка 1: `kscreenlocker_greet` — ложный след (потрачено большинство ночи)

Изначально предполагалось, что виноват стандартный `kscreenlocker_greet`
(классический экран блокировки KDE) — маскировали его на `/bin/true`,
потом заменяли на wrapper с `QT_QUICK_BACKEND=software`. **Проверено
через `journalctl _COMM=kscreenlocker_greet` — НОЛЬ записей за всю
загрузку.** Этот процесс вообще ни разу не запускается в
`plasma-mobile-wf`. Все патчи вокруг него — потраченное время, реальная
причина в другом.

## Находка 2: реальный источник — `WayfireTweaks.qml` (свой, не kscreenlocker)

`plasma-mobile-wf` (droidian-форк с wayfire) использует СОБСТВЕННЫЙ
механизм блокировки, не связанный с `kscreenlocker`:

- `WayfireTweaks.qml` (`.../qt6/qml/org/kde/plasma/private/mobileshell/
  WayfireTweaks.qml`) — `Component.onCompleted` **всегда** вызывает
  `SessionLockPlugin.SessionLock.requestLock()` при каждом старте сессии
  (плюс по кнопке питания, плюс по таймауту простоя через
  `WayfireIpcPlugin.WayfireIPC.onIdleTimout`). Показывает
  `LockScreenSplash.qml` (простой Layer-Shell оверлей, чёрный фон +
  иконка + текст, БЕЗ поля ввода, `keyboardInteractivity: None`) сразу,
  и должен скрыть его когда `SessionLock.locked` станет `false`.
- `DeviceLock.qml` — отдельный, второй путь: `triggerLock()` вызывает
  `MobileShellState.LockscreenDBusClient.lockScreen()` — нативный
  C++/D-Bus метод, НЕ через `SessionLockPlugin`. Кто именно вызывает
  `DeviceLock.triggerLock()` — не установлено (компилируется в
  `libmobileshellplugin.so`, не нашли текстовым поиском).
- Реальный экран ввода PIN (с полем, но без видимой кнопки подтверждения
  — баг сам по себе, недорисован UI) — это, судя по всему, ТРЕТИЙ
  компонент, не `LockScreenSplash` (у того нет поля ввода вообще).
  Не идентифицирован окончательно.

## Находка 3 (ключевая для будущих live-патчей!): QRC-embedded QML игнорирует файлы на диске

`qmldir` модуля `org.kde.plasma.private.mobileshell` содержит:
```
prefer :/org/kde/plasma/private/mobileshell/
```
Это заставляет движок QML **всегда** брать файлы из QRC-ресурса,
скомпилированного прямо в `libmobileshellplugin.so`, ИГНОРИРУЯ файлы на
диске — даже при том, что `qmldir` явно регистрирует
`WayfireTweaks 254.0 WayfireTweaks.qml` как обычный тип. Подтверждено:
`strings libmobileshellplugin.so | grep -c "Locking..."` → 1 (строка
реально зашита в бинарник).

**Это значит: ЛЮБОЙ live-патч файла внутри
`.../mobileshell/*.qml` через простой `cp`/remount,rw НЕ РАБОТАЕТ**, пока
не будет также убрана строка `prefer` из `qmldir` того же модуля — тот
же паттерн, что мы уже нашли для `KRunnerScreen.qml` (телефония,
исправлено пересборкой `plasma-dialer`) и `ResultsListView` (`milou`,
исправлено пересборкой `milou`). Для `mobileshell` полная пересборка
`libmobileshellplugin.so` НЕ делалась — вместо этого испробован
эксперимент: удалить строку `prefer` из `qmldir` целиком, чтобы движок
откатился на файлы диска для ВСЕХ типов модуля (не только
`WayfireTweaks`). Результат неоднозначный — экран блокировки стал
появляться не всегда (периодически), но не исчез до конца; возможно,
из-за второго независимого пути (`DeviceLock`) или из-за того что
`prefer` влияет ещё на что-то, что мы не учли.

## Опробованные фиксы (промежуточные, не финализированные)

1. `WayfireTweaks.qml` на диске отредактирован — убраны все 3
   вызова `SessionLock.requestLock()` (onCompleted, onPwrKeyStateChanged,
   onIdleTimout), логика диммирования экрана оставлена нетронутой.
   **Файл лежит только на устройстве живьём, НЕ добавлен в в5** (сессия
   прервана перезагрузкой раньше, чем успели зафиксировать).
2. `qmldir` модуля mobileshell — строка `prefer` удалена (тот же live,
   не в в5).
3. `session-lock` убран из `plugins =` в `wayfire.ini` (блокирует сам
   протокол `ext-session-lock-v1` на уровне композитора) — тоже live,
   не в в5. **Не помогло само по себе** (экран продолжал появляться
   даже без этого протокола — подтверждает что минимум один путь идёт
   в обход wayfire-уровня, скорее всего через `DeviceLock`/D-Bus).
4. `wayfire`'s `window-rules` плагин НЕ умеет матчить layer-shell
   поверхности (только обычные xdg-toplevel окна) — эта идея отпала,
   проверено через документацию.

## Что НЕ помогло / отброшенные идеи

- Маскирование/обёртка `kscreenlocker_greet` — вообще не тот процесс.
- `kscreenlockerrc` (`Autolock=false` и т.д.) — не влияет, поскольку
  блокировка не идёт через стандартный kscreenlocker вообще.
- `HandlePowerKey=lock/ignore` в `logind.conf` — отдельная история про
  кнопку питания (решена, см. ниже), не связана с этим багом напрямую.

## Побочная находка: `HandlePowerKey`

Дефолт `systemd-logind` для короткого нажатия кнопки питания —
`poweroff` (не блокировка!). На этом устройстве при `poweroff` во время
зарядки PMIC/прошивка сразу включает телефон обратно — выглядит как
"ушёл на перезагрузку". **Не зафиксировано в в5** (эксперимент с
`HandlePowerKey=lock`, потом откачен обратно на `ignore` из-за побочных
эффектов рестарта logind — см. ниже).

## КРИТИЧЕСКИ ВАЖНО: перезапуск `systemd-logind` ломает живую сессию

Уже задокументированный ранее (`DROIDIAN-V23-PLAN.md`) паттерн
подтверждён ещё раз: `systemctl restart systemd-logind` **рвёт**
libseat-сессию `wayfire`/`kwin_wayland`, контейнер `android` и связанные
systemd-юниты уходят в `failed`. Восстановление: `systemctl
reset-failed`, `halium-gpu-bridge-setup.sh`, `systemctl start
plasma-mobile-wf.service`, заново наложить touch-bind + EGL-патч.
**Устанавливать `HandlePowerKey` НЕ перезапуская logind не получится**
(логind сам не перечитывает конфиг без restart/reload) — так что смена
этой настройки всегда сопряжена с этим риском на данном образе.

## `seatd` — подтверждённо работает и решает основную нестабильность

`seatd.service` уже встроен в образ с версии v18 (`etc/default/seatd`,
`usr/bin/seatd-launch`, `usr/sbin/seatd`,
`usr/lib/systemd/system/seatd.service` — все уже в `в5/halium-extras/
rootfs-files/`). Подтверждено в журнале:
```
[libseat] [libseat/libseat.c:73] Seat opened with backend 'seatd'
```
`wayfire` использует его успешно вместо `logind`-бэкенда — устраняет
тот самый многомесячный баг "теряет seat через ~20с"
(см. `DROIDIAN-V23-PLAN.md`, "ЗАДАЧА 17"). Именно это, похоже, и
объясняет, почему `plasmashell` сегодня несколько раз держался
стабильно 100+ секунд подряд — раньше такого не было.

## УСПЕХ (2026-07-31, позже той же ночи): рабочий стол загружается без экрана блокировки

Комбинация фиксов 1+2 (обрезка `requestLock()` в `WayfireTweaks.qml` +
удаление `prefer` из `qmldir` модуля mobileshell, чтобы движок реально
читал файл с диска, а не вкомпилированный QRC-ресурс) — **подтверждена
рабочей живьём**, несколько раз подряд после чистой перезагрузки.
Рабочий стол открывается сразу, без зависшего "Locking...".

Оба файла (`usr/lib/aarch64-linux-gnu/qt6/qml/org/kde/plasma/private/
mobileshell/{WayfireTweaks.qml,qmldir}`) добавлены в `в5/halium-extras/
rootfs-files/` как окончательные постоянные файлы.

**`DeviceLock.qml`/`LockscreenDBusClient` путь оказался НЕ проблемой** —
судя по всему, ничего его в действительности не дёргало, весь симптом
объяснялся первыми двумя находками (kscreenlocker_greet вообще не
использовался, реальный триггер был в WayfireTweaks.qml, но
маскировался QRC-приоритетом).

## ДОПОЛНИТЕЛЬНО: полная автозагрузка настроена и протестирована

По просьбе пользователя убран весь ручной "gate" — теперь всё поднимается
само после `reboot`, без единой ручной SSH-команды:

1. **`lxc@android.service`** — включён (`systemctl enable`), симлинк в
   `в5/halium-extras/rootfs-files/etc/systemd/system/
   multi-user.target.wants/`.
2. **Тач-бинд** (`synaptics_ts` i2c) — вшит прямо в конец
   `halium-gpu-bridge-setup.sh` (уже вызывается как `ExecStartPre` у
   `android-service@hwcomposer.service`, отдельный юнит не понадобился).
3. **EGL-патч** (`QT_QUICK_BACKEND=software` + пустой
   `QT_WAYLAND_CLIENT_BUFFER_INTEGRATION`) — вшит напрямую в
   `usr/bin/startplasmamobile` как обычный файл (НЕ bind-mount из
   `/tmp` — те не переживают перезагрузку).
4. **Реальная гонка найдена и исправлена**: `android-service@hwcomposer.
   service` стартует по `After=lxc@android.service`, но это гарантирует
   только что юнит СТАРТОВАЛ, не что контейнер УСПЕЛ примонтировать
   свой rootfs на хосте (`/android/system/system`, `/android/vendor`).
   `halium-gpu-bridge-setup.sh` раньше делал bind этих путей с простым
   `|| true` — тихо проваливался, если источник ещё не готов, БЕЗ
   повторной попытки. Добавлен wait-цикл (по образцу уже существующего
   для firmware) — ждёт `/android/system/system/etc` и
   `/android/vendor/firmware` перед bind-mount, до 10 секунд.
5. Дополнительно как подстраховка — `Restart=on-failure` +
   `RestartSec=1` + `StartLimitBurst=30` для
   `android-service@hwcomposer.service` (drop-in
   `50-retry-container-race.conf`) — на случай если гонка всё же
   когда-нибудь произойдёт несмотря на wait-цикл.

**Подтверждено чистой перезагрузкой**: `plasmashell`/`wayfire`
поднимаются сами, рабочий стол виден, без единой ручной команды.

**Известный, не до конца объяснённый глюк**: один раз EGL-патч в
`usr/bin/startplasmamobile` пропал сам по себе между двумя проверками
(файл "потерял" две строки после которой-то перезагрузки, несмотря на
то что был скопирован как обычный файл, не bind-mount). Причина не
установлена (возможно, гонка между `remount,rw`/`remount,ro`
операциями и другим процессом, писавшим в тот же файл в этот момент).
Обнаружено и исправлено повторным `sed`, но стоит перепроверить
устойчивость этого файла в следующих сессиях.

## ВАЖНАЯ НАХОДКА: `remount,rw` правки `/etc` на живой системе НЕНАДЁЖНЫ

Несколько раз за ночь правки, сделанные через `mount -o remount,rw /`
+ `cp`/`sed` + `mount -o remount,ro /` на УЖЕ ЗАГРУЖЕННОЙ системе (не
через TWRP), пропадали после следующей перезагрузки без видимой
причины: EGL-патч в `usr/bin/startplasmamobile` один раз "потерял" две
строки, retry-дропин `android-service@hwcomposer.service.d/
50-retry-container-race.conf` дважды откатывался на старое содержимое.
При этом файлы, залитые через **TWRP** (`adb push` + `mount -o
loop,rw` на `/data/rootfs.img` напрямую, устройство выключено) —
переживали перезагрузки стабильно все разы без исключений.

**Вывод на будущее**: любую правку, которая должна пережить
перезагрузку, нужно в конце концов залить через TWRP-инъекцию на
`/data/rootfs.img` (как делали для основного финального прохода) — live
`remount,rw` годится только для быстрого тестирования В ТЕКУЩЕЙ
сессии, не для постоянного результата. Причина ненадёжности не
установлена (возможно, гонка с каким-то фоновым процессом, который
периодически восстанавливает `/etc` из снапшота/upperdir теряет
изменения при определённых сценариях remount).

## НОВЫЙ ОТКРЫТЫЙ БАГ (2026-07-31, конец ночи): экран не просыпается по кнопке питания

**Симптом**: экран гаснет через 60 секунд простоя (`dpms_timeout = 60` в
`wayfire.ini`, `[idle]`) — это ожидаемое поведение. Но короткое нажатие
кнопки питания **ненадёжно возвращает экран** — иногда включается на
секунду и гаснет снова, иногда не включается вовсе. Прямая запись в
`/sys/class/backlight/panel0-backlight/{bl_power,brightness}` НЕ
помогает (значения принимаются, но `actual_brightness` остаётся 0) —
похоже, `wayfire` сам продолжает передавливать состояние через свой
DPMS-протокол. **Единственный надёжный воркэраунд, найденный сегодня**:
`systemctl restart plasma-mobile-wf.service` — полный рестарт шелла
сбрасывает внутреннее DPMS-состояние и возвращает экран, но это,
конечно, не решение для реального использования.

**Дополнительная находка (важная зацепка для следующей сессии)**:
пользователь заметил, что экран гаснет по таймауту **даже при активном
касании** — то есть тач не сбрасывает `idle`-таймер `wayfire`. Проверил
исходник `plugins/single_plugins/idle.cpp` — плагин слушает общий
`wf::seat_activity_signal`, никакой явной фильтрации по типу устройства
на уровне плагина нет; значит либо баг в том, КАК/КОГДА touch-события
эмиттят этот сигнал на уровне ядра `wayfire` (не в плагине), либо
что-то в НАШЕЙ конфигурации (`hybris`/touch-bridge) не пробрасывает
touch-события туда, откуда `seat_activity_signal` вообще эмиттится.
Не исследовано глубже из-за позднего часа.

**Отдельно**: один раз после пробуждения (после ввода 0000 в
неожиданно появившемся запросе пароля) экран ушёл в чёрный вместо
рабочего стола — возможно, это НЕ баг с блокировкой (та подтверждена
отключённой, 0 `requestLock` в `WayfireTweaks.qml`), а тот же самый
DPMS-баг, просто совпавший по времени с попыткой разблокировки.
Не до конца отделено одно от другого.

**Ещё наблюдение**: после очередного рестарта шелла экран гас уже
примерно через ~30 секунд — короче настроенных `dpms_timeout = 60` в
`wayfire.ini`, и короче 5 минут, которые пользователь незадолго до
этого выставил через System Settings → Энергосбережение. Либо
изменение через System Settings не применяется реально (сохраняется в
`powermanagementprofilesrc`, но `wayfire`'s `idle`-плагин продолжает
использовать своё собственное `dpms_timeout` из `wayfire.ini`,
никак не связанное с KDE Power Management), либо таймер вообще путается
между несколькими независимыми механизмами (`wayfire` `idle`-плагин
vs `powerdevil`). Также обнаружено (см. выше): при частых рестартах
шелла накапливаются осиротевшие `kwin_wayland_wrapper` процессы,
не подчищенные предыдущими сессиями — возможная косвенная причина
общей нестабильности сессии.

## Следующие шаги (для следующей сессии)

1. **Определить, кто вызывает `DeviceLock.triggerLock()`** — либо через
   `qmlRegisterSingletonType`/сигнал где-то в компилированном
   `libmobileshellplugin.so` (нужен `objdump`/`nm` на самом .so, либо
   поиск в исходниках `plasma-mobile-wf` — `github.com/droidian/
   plasma-mobile-wf`, ветка `group/next/plasma-6.5`,
   `components/mobileshell/qml/wayfiretweaks/WayfireTweaks.qml` и
   соседние файлы в том же каталоге `components/mobileshell/qml/`).
2. Если решим убирать блокировку насовсем (финальное решение
   пользователя на эту ночь: "убрать блокировку насовсем, если что
   потом включить через настройки") — самый надёжный вариант это
   ПОЛНАЯ пересборка `libmobileshellplugin.so` из исходников с уже
   готовым патчем `WayfireTweaks.qml` (описан выше, working copy жил
   только на устройстве). Зависимости сборки СУЩЕСТВЕННО больше, чем у
   `plasma-dialer`/`milou` — требует `KWin` (сама библиотека, не просто
   KF6-модуль), `LibKWorkspace`, `KSysGuard`, `PlasmaActivities`,
   `QCoro6`, `KPipeWire` и ещё десяток пакетов. Риск ABI-нестыковок
   выше, объём работы больше на порядок. НЕ начато.
3. Альтернатива (быстрее, но менее надёжно): найти способ убрать
   именно `DeviceLock`'s триггер, если он окажется вызываемым из
   ДРУГОГО, более простого QML-файла (не факт).
4. Как временный live-воркэраунд для тестирования (НЕ для финальной
   прошивки): комбинация "убрать `prefer` из `qmldir` + патчить
   `WayfireTweaks.qml` на диске" снижает частоту появления экрана, но
   не убирает полностью — вероятно из-за пути через `DeviceLock`.
