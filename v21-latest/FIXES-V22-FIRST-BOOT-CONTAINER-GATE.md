# v22: гейт автостарта Android-контейнера на первую загрузку (2026-07-27)

## Контекст

Первая живая прошивка v21 (после сегодняшней сборки). Обнаружено два
независимых бага:

1. **chroot-установка аудио-стека падала с `dpkg: not found` (exit 127)**.
   Причина: TWRP-шелл (тот, что запускает `update-binary`) имеет
   `PATH=/sbin:/system/bin` -- без `/usr/bin`, где лежит `dpkg` в
   Debian-образе. `chroot` сам по себе не сбрасывает/не переопределяет
   `PATH`, просто наследует окружение вызывающего процесса.
   **Исправлено**: добавлен явный `export PATH=...` в начало
   chroot'нутого `/bin/sh -c '...'` в `update-binary`.

2. **Первая загрузка после флеша не стартовала** (чёрный экран /
   зависание, USB не поднимался вообще). Диагностика через TWRP:
   - `/sys/fs/pstore/console-ramoops-0` не показал НИ ОДНОЙ panic/oops/
     watchdog-reset записи -- только безобидный, ожидаемый шум от
     Android-контейнера (`Could not restart 'audioserver'/'cameraserver'/
     'media'` -- это НАРОЧНО отключенные через `_HYBRIS_DISABLED`
     сервисы, штатное поведение) вплоть до ~98с аптайма.
   - Живой тест: замаскировали `lxc-android-config.service` и
     `halium-start-container-delayed.service`/`.timer` напрямую в
     смонтированном через TWRP `rootfs.img` (`mount -t ext4 -o rw
     /data/rootfs.img /mnt_rootfs`) -- то есть Android-контейнер
     полностью отключён от автостарта.
   - Дополнительно нейтрализован `/data/halium-restore-state.sh`
     (персистентный, `/userdata` = то же самое что TWRP видит как
     `/data`) -- иначе он бы пересоздал те же юниты с реальным
     содержимым на следующей загрузке поверх маски.

## Постоянное решение: булевый флаг PHOSH_FIRST_BOOT_OK

По просьбе пользователя вместо разовой ручной маскировки сделан
постоянный механизм в самом v22:

**Идея**: на первой загрузке после переflash-а (самой нестабильной --
chroot-установка ещё не гарантированно успешна, Android HAL может
крашиться массово) Android-контейнер НЕ стартует вообще, давая
host-стороне (systemd + Phosh) шанс подняться абсолютно чисто, без
конкуренции за ресурсы/binder/логи с контейнером. Спустя 55 секунд
после boot (просто по таймеру, без привязки к обнаружению
shell-клиента Phosh -- проще и надёжнее) -- считаем, что host-сторона
уже успела подняться, ставим флаг и поднимаем контейнер.

### Реализация (финальная версия, по итогам обсуждения)

**`/userdata/halium-restore-state.sh`** -- блок создания
`halium-start-container-delayed.service`/`.timer` теперь двусторонний
`if`/`else`, гейт по `/userdata/PHOSH_FIRST_BOOT_OK`:
```sh
if [ -f /userdata/PHOSH_FIRST_BOOT_OK ]; then
    # обычные юниты контейнера (halium-start-container-delayed,
    # 15с-таймер) -- как было раньше, без изменений
else
    # НОВОЕ: одноразовый юнит halium-first-boot-container-start,
    # 55с-таймер, создаётся ТОЛЬКО в этой ветке
fi
```
Ключевое: обе ветки взаимоисключающие -- на любой конкретной загрузке
создаётся ЛИБО обычный контейнерный таймер (флаг уже есть), ЛИБО
новый 55с-таймер (флага ещё нет), никогда оба сразу и никогда ни
одного. Юниты живут в `/etc` (tmpfs, пересоздаётся с нуля из этого
скрипта каждую загрузку) -- то есть на 2-й и последующих загрузках
55с-таймер НЕ просто ничего не делает при срабатывании, а **вообще не
существует как systemd-юнит**.

**`halium-extras/libexec/halium-first-boot-container-start.sh`** --
новый скрипт, запускается через `halium-first-boot-container-start.
service`/`.timer` (`OnBootSec=55s`), которые создаёт else-ветка выше.
Логика: если `/userdata/PHOSH_FIRST_BOOT_OK` уже есть -- сразу exit 0
(доп. подстраховка, хотя юнит и так не должен существовать в этом
случае). Иначе: создаёт маркер `PHOSH_FIRST_BOOT_OK` (навсегда), затем
живьём создаёт и стартует настоящий `halium-start-container-delayed.
service` -- контейнер поднимается в этом же боте, без лишнего ребута.

(Более ранний вариант -- вешать это на `halium-phosh-watchdog.sh`,
детектируя реальный shell-клиент Phosh -- был реализован, но заменён
на простой таймер по прямой просьбе пользователя: проще и не зависит
от точности detect-логики. Правка в halium-phosh-watchdog.sh
полностью откачена обратно к оригиналу.)

### Как это ведёт себя по загрузкам

- **Загрузка 1 (сразу после flash)**: маркера нет -> `halium-restore-
  state.sh` создаёт ТОЛЬКО 55с-таймер, обычный контейнерный таймер не
  создаётся вообще -> Phosh поднимается на чистом host-стеке -> через
  55с таймер сам ставит флаг и поднимает контейнер живьём.
- **Загрузка 2 и далее**: маркер уже есть -> создаётся ТОЛЬКО обычный
  15с контейнерный таймер (как было всегда), 55с-таймер не создаётся
  вообще -- механизм первой загрузки полностью отсутствует в системе.

### Как проверить/сбросить вручную

- Убедиться что сработало: `cat /userdata/halium-first-boot-gate.log`
  должен содержать строку "55s first-boot timer fired".
- Повторно проверить "первую загрузку" на уже настроенном устройстве:
  `rm /userdata/PHOSH_FIRST_BOOT_OK` + reboot.

## Статус
Реализовано и синтаксически проверено (`sh -n`) для четырёх файлов:
`update-binary`, `halium-restore-state.sh`,
`halium-first-boot-container-start.sh`, `halium-phosh-watchdog.sh`
(последний -- откат к оригиналу, без изменений по факту).
**НЕ протестировано живьём** -- следующий flash v22 будет первым
реальным тестом всего механизма разом (PATH-фикс chroot + гейт по
PHOSH_FIRST_BOOT_OK через 55с-таймер).

## Живой инцидент сегодня (v21, до появления этого механизма в v22)

На реальном v21-флеше первая загрузка зависла (USB не поднимался
вообще). Через TWRP подтвердили отсутствие panic/oops в pstore --
безобидный ожидаемый шум от `_HYBRIS_DISABLED`-сервисов вплоть до
~98с аптайма, без явного краха. Вручную замаскировали автостарт
контейнера прямо в смонтированном `rootfs.img` + нейтрализовали
`/data/halium-restore-state.sh` временным маркером
`/userdata/DISABLE_CONTAINER_AUTOSTART` (эта временная переменная --
разовый костыль для v21, в постоянный механизм v22 НЕ вошла, заменена
на `PHOSH_FIRST_BOOT_OK` с обратной семантикой). После перезагрузки
host-сторона поднялась чисто, Phosh показал рабочий стол. Контейнер
запущен вручную командой `systemctl start halium-start-container-
delayed.service` -- поднялся успешно (`lxc-info`: `State: RUNNING`).
Аудио при этом всё ещё не работает, т.к. chroot-установка пакетов
провалилась (см. выше) и живого fallback-скрипта на этом v21-флеше
для проверки уже не осталось -- фикс PATH пойдёт только в v22.
